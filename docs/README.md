## Rebuilding the figures

Every figure is produced by the code itself rather than drawn, so a figure that
stops matching the code is a one-command fix:

```bash
./fv2d.sh mesh @transonic figure=docs/figures/mesh.png
./fv2d.sh geometry airfoil=0012 figure=docs/figures/section.png normals=yes
```

There is no figure build step and no CI checking them, so this is a **manual
step after changing the geometry or the mesh generator**. Nothing breaks if you
forget: the committed PNG simply stops matching the code, which is a
documentation bug rather than a solver one.

## On colour maps

`src/plotting.py` refuses `jet`, `rainbow`, `hsv` and the other
non-monotonic maps by name. `legacy/plotsolution.m` drew the Mach field with
`jet`, and a rainbow map puts structure in a picture that is not in the data:
its lightness is non-monotonic, so it invents visual edges at the yellow and
cyan bands — which on a transonic field is indistinguishable from the shock the
figure exists to show. The project map is `magma`, which rises monotonically in
lightness, so a brighter pixel is a larger value everywhere and the figure
survives greyscale printing and a colour-blind reader.
